# Algo Arena authentication setup

The app uses its existing Better Auth and Prisma session/account tables. Google sign-in is optional; email and password continue to work when Google credentials are absent. No Passport or second session store is introduced.

## Local setup

1. Copy `apps/api/.env.example` to `apps/api/.env` and `apps/web/.env.local.example` to `apps/web/.env.local`.
2. Start PostgreSQL with `pnpm db:up` from the repository root. The database is exposed at `localhost:5434` for the API's example `DATABASE_URL`.
3. Run `pnpm --filter @practice/api prisma:migrate` once, then `pnpm dev` from the root. Judge0 is needed only for code execution; start it with `pnpm judge0:up` when required.
4. In [Google Cloud Console](https://console.cloud.google.com/), select or create a project. Open **Google Auth Platform → Branding** and set the app name, support email, and developer contact email. Under **Audience**, choose the audience that matches your app. While the app is in testing, add the Google accounts you will use under **Test users**.
5. Open **Google Auth Platform → Clients → Create client**. Select **Web application**, give it a recognizable name, and add `http://localhost:3000` under **Authorized JavaScript origins**.
6. Under **Authorized redirect URIs**, add this exact callback: `http://localhost:4000/api/auth/callback/google`. It must match `GOOGLE_CALLBACK_URL` character for character, including scheme, host, port, and path. Google documents that a mismatch causes `redirect_uri_mismatch`.
7. Create the client. In the resulting dialog, copy **Client ID** and **Client secret**. The secret is generated by Google when you create the web OAuth client; it is not the client ID and cannot be generated inside Algo Arena. Google may show the secret only at creation time, so store it securely. If it is lost or exposed, create a new client secret in the Cloud Console and replace the API value.
8. Put the ID and secret in `apps/api/.env` only. Example:

   ```dotenv
   GOOGLE_CLIENT_ID=your-client-id.apps.googleusercontent.com
   GOOGLE_CLIENT_SECRET=your-google-client-secret
   GOOGLE_CALLBACK_URL=http://localhost:4000/api/auth/callback/google
   ```

   Set `NEXT_PUBLIC_GOOGLE_OAUTH_ENABLED=true` in `apps/web/.env.local` to show the Google button. Never put the client secret in a `NEXT_PUBLIC_` variable or commit it. Restart both services after changing environment values.

Google OAuth uses Better Auth's popup plugin. The Google consent flow opens separately, verifies the popup message origin, and refreshes the app session. After successful sign-in or sign-up, the app takes the user to `/questions` (and keeps the current problem open when signing in from its workspace). If the popup is blocked, allow popups for the app and retry. Email/password uses client requests and then follows the same destination behavior.

## Sign-in checks

- Visit `/signin` or `/signup`, submit valid email/password details, and confirm the app opens `/questions`.
- Try invalid credentials and confirm an inline error appears without leaving the auth page.
- With Google configured, use **Continue with Google**, choose an account, and confirm the popup closes and the navbar updates in place.
- Sign out and confirm the session clears. Authenticated users can run and submit from `/questions/<slug>`.

The API emits a startup warning and leaves Google unavailable when either Google credential is missing. Keep secrets only in local environment files; do not commit them.
